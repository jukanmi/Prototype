# 웨이브 저작 리팩터링 계획 — 웨이브를 SO로, 스폰 지점을 씬으로

> 상태: **완료.** 8단계까지 전부 끝났다. 웨이브 애셋이 원본이고 하드코딩 표는 없다.
> 관련 코드: `Assets/Scripts/Stage/Wave.cs`, `StageDirector.cs`, `EnemySpawnService.cs`, `Spawn.cs`

---

## 0. 무엇을 바꾸는가

웨이브 배치가 지금은 `StageWaveCatalog`에 하드코딩된 C# 표다. 이걸 **웨이브 하나 = 애셋 하나**로 옮기고,
등장 위치를 씬의 실제 지점으로 지정할 수 있게 만든다.

한 줄로: **웨이브 내용은 프로젝트 애셋에, 스폰 지점은 씬에, 둘을 잇는 다리는 씬 컴포넌트 하나.**

| 있는 것 | 하는 일 | 이번 계획에서 |
| --- | --- | --- |
| `StageWaveCatalog` | 스테이지별 웨이브 표를 코드로 들고 있다 | 배치는 **없어진다**. 스테이지 지형만 남는다 |
| `WaveSpawn` | `role/count/side/delay/interval/elite` 묶음 한 줄 | **`WaveSpawnEntry`로 대체** — 한 줄 = 한 기 |
| `WaveSpawnPlanner.Plan` | 묶음 안 순번으로 배치 | `PlanAuto` · `PlanAt`으로 대체 |
| `WaveSpawnPlanner` | 역할별 좌표 계산. 순수 정적 함수 | **순번 정의가 바뀐다** — 묶음 안 순번 → 역할별 통산 번호 |
| `StageDirector` | 번호로 표를 읽어 큐에 밀어넣는다 | 씬의 보드를 읽는다 |
| `EnemySpawnService` | 벽 진입 · 화면 밖 진입 두 메서드 | 모션을 인자로 받는 **창구 하나**로 합친다 |
| `SpawnEntry` / `EnemySpawnGuard` / `SpawnTelegraph` | 진입 연출과 예고 | 그대로. 땅속 돌출이 이걸 재사용한다 |

## 1. 왜 이 모양인가 — 검토하고 버린 두 안

### 버린 안 A. 웨이브 애셋이 Transform을 직접 든다

**불가능하다.** ScriptableObject는 프로젝트 애셋이고, 씬 오브젝트 참조를 넣으면 유니티가
저장 시점에 null로 지운다. 기획서의 "등장 위치 = Transform"을 문자 그대로는 구현할 수 없다.

### 버린 안 B. 씬마다 디렉터를 새로 만들어 웨이브를 직접 넣는다

Transform은 살아난다. 대신 셋을 잃는다.

1. **기계 배선이 복제된다.** 지금 프리팹이 든 것은 적 데이터 참조 셋, 진입 비행 시간,
   강화 배율, 웨이브 간격이다. 웨이브와 무관한 값인데 씬 수만큼 복사된다. 강화 배율을
   내리면 씬을 전부 열어야 하고, 하나를 빠뜨리면 그 스테이지만 다르게 도는데 화면으로는 안 보인다.
2. **테스트가 못 본다.** `StageWaveCatalogTests`가 261줄이고 스스로 "기획서의 사본"이라고 적어 놨다.
   표가 씬으로 들어가면 그 검증이 통째로 사라진다.
3. **씬 파일이 자주 바뀐다.** 웨이브 한 줄을 고쳐도 씬 텍스트가 바뀐다. 씬은 병합 충돌이 나면
   손으로 풀기 가장 나쁜 파일이다.

### 고른 안. 절반만 씬으로 내린다

웨이브 **내용**은 애셋에 남기고, 웨이브 **목록**과 **지점 표**만 씬 컴포넌트 하나로 내린다.
디렉터 프리팹은 기계로 그대로 둔다. 프리팹 인스턴스의 배열 오버라이드가 아니라
별개 오브젝트라 병합 함정이 없고, 웨이브를 아무리 편집해도 프리팹이 안 더러워진다.

## 2. 자료 구조

### 2.1 프로젝트 애셋 층

```csharp
// 애셋. 자기 필드를 직접 든다.
class WaveAsset : ScriptableObject
{
    string            label;
    WaveAdvance       advance;      // 다음 웨이브 실행 조건
    int               attackTokens;
    WaveSpawnEntry[]  spawns;
    // 지속 리젠 필드
}

// 한 줄 = 적 한 기.
struct WaveSpawnEntry
{
    EnemyRole   role;
    bool        elite;
    SpawnOrigin origin;     // Auto | Point
    string      pointId;    // origin == Point 일 때만 읽는다
    float       appearAt;   // 웨이브 시작 기준. 연출이 시작되는 시각이다
    SpawnMotion motion;     // FlyIn | FromWall | Burrow
    SpawnSide   side;       // origin == Auto 일 때만 읽는다
}

enum SpawnOrigin { Auto, Point }
enum SpawnMotion { FlyIn, FromWall, Burrow }
enum WaveAdvance { AllCleared, TargetKilled }
```

**`WaveAsset`이 옛 정의 타입을 감싸지 않은 이유.** 초안에서는 정의 한 칸만 든 껍데기로 잡았다가
구현하면서 뒤집었다. 감싸면 애셋이 옛 묶음 형식을 물고 태어나고, 그렇다고 정의에 새 형식을
같이 넣으면 한 타입이 두 형식을 들게 된다. 옛 정의는 8단계에서 사라질 예정이었으므로
처음부터 최종 모양으로 두는 편이 짧았다. **결과적으로 맞았다** — 8단계에서 애셋은 한 줄도 안 고쳤다.

**enum의 0번 값이 곧 현행 동작이어야 한다.** 인스펙터에서 줄을 새로 추가하면 모든 칸이 0으로
직렬화된다. `Auto`, `FlyIn`, `AllCleared`가 각각 0번이라 새 줄은 지금과 똑같이 돈다.
순서를 바꾸면 이미 저작된 애셋의 뜻이 조용히 바뀐다.

### 2.2 씬 층

방 하나에 **보드 컴포넌트 하나.** 두 가지를 든다.

- 이 방이 순서대로 돌 `WaveAsset` 목록
- 이름과 `Transform`을 짝지은 **스폰 지점 표**

이 표가 애셋과 씬을 잇는 유일한 다리다. 지점 자체는 빈 게임오브젝트고 표의 각 줄이 그걸 가리킨다.

### 2.3 프리팹 층

`StageDirector`와 `EnemySpawnService`는 지금 프리팹 그대로. 적 데이터 배선, 진입 비행 시간,
강화 배율, 웨이브 간격이 여기 남는다. `stageNumber`는 로그와 주제 문구에만 쓰고
웨이브를 고르는 데는 더 이상 안 쓴다.

디렉터는 시작할 때 씬에서 보드를 찾는다. `PartySpawnPoint`가 이미 같은 규약이다.

**보드가 없거나 목록이 비면 에러를 찍고 그 스테이지를 멈춘다. 번호로 몰래 폴백하지 않는다.**
3 · 4 스테이지가 1번 표로 돌던 버그(`c325639f`)가 정확히 그 조용한 폴백에서 나왔다.

### 2.4 스폰 창구를 하나로

지금 `EnemySpawnService`에 `SpawnFromWall`과 `SpawnAtEdge`가 갈라져 있다. 모션이 셋이 되면
갈래가 셋이 된다. 모션을 인자로 받는 메서드 하나로 모으고 안에서 분기시킨다. 아레나도 같은 창구를 쓴다.

## 3. 조용히 깨지는 곳

### 3.1 마릿수가 사라진다

지금 한 줄이 여러 기를 낳고, **묶음 안 순번**이 좌우 교대(`SideSign`)와 깊이 줄
로테이션(`MeleeLanes`, `ChargerLaneOffsets`)의 입력이다. 한 줄이 한 기가 되면 그 순번이 없어진다.
아무 대책 없이 전부 0번으로 두면 전사 다섯이 전부 같은 줄에 겹쳐 선다.

**순번은 웨이브 안에서 역할별로 센다.** 통짜 번호는 안 된다 — 줄 로테이션 표가 역할마다
따로기 때문이다. 통짜로 세면 마법사 둘의 상하가 뒤집히고, 무엇보다 **돌진전사의 0번
(플레이어와 같은 줄)이 앞 역할의 마릿수에 따라 밀린다.** 깊이 회피를 강제하려고 만든 규칙이
조용히 죽는 자리다. 그리고 **씬 지점을 쓰는 줄은 순번을 소비하지 않는다.** 소비하게 두면
지점 한 줄을 끼워 넣는 것만으로 나머지 자동 배치가 통째로 밀린다.

역할별로 세면 기존 아홉 웨이브 중 여덟이 좌표가 한 톨도 안 바뀐다. 남은 하나가 1-B인데,
거기서는 **일부러 달라지고 그게 고침이다.** 강화 전사 1기와 전사 2기가 두 묶음으로 나뉘어 있어
예전 규칙이 두 묶음의 0번을 같은 자리에 세웠다. 등장 시각만 다를 뿐 걸어가는 목적지가 같아서,
먼저 온 쪽에 막힌 뒤쪽이 도착 판정을 못 받고 걷기 제한 시간까지 밀린다.

### 3.2 플레이어 추종 배치가 죽는다

돌진전사는 플레이어와 같은 깊이 줄에 서고(`DepthFor`의 `Charger`), 마법사는 반대로 그 줄을
피한다. 이게 깊이 회피를 강제하는 레벨 디자인 규칙이다. 지정 지점으로 못 박으면 사라진다.

그래서 **위치 소스의 기본값은 `Auto`**고, `Point`는 의도가 있을 때만 쓴다.

### 3.3 지점 이름은 문자열이라 오타가 컴파일에 안 걸린다

보드 표에 없는 이름을 찾으면 에디터 검증에서 먼저 잡고, 런타임에는 자동 배치로 떨어뜨린 뒤
경고를 남긴다. 조용히 원점에 소환하면 원인이 안 보인다.

### 3.4 땅속 돌출은 예고가 필수다

발밑에서 튀어나오는 적은 예고 없이는 부당하게 읽힌다. 후방 스폰 예고 표식(`SpawnTelegraph`)을
발밑에 띄우고, 예고 없는 돌출은 검증에서 막는다.

### 3.5 확정한 두 가지

- **등장 시각은 연출 시작 시각이다.** 참전 시각이 아니다. 모션별 소요 시간은 인스펙터에
  드러내고 로그에 실제 참전 시각을 찍는다. 두 뜻이 섞이면 저작자가 표를 못 믿는다.
- **지속 리젠은 웨이브 애셋에 그대로 둔다.** 조건 축으로 흡수하려면 트리가 필요한데
  그건 이번에 건너뛰기로 한 부분이다.

### 3.6 뒤늦게 잡힌 배치 겹침 두 건

8단계에서 "구운 웨이브 전부를 배치해 보고 두 기가 같은 자리에 서지 않는지" 보는 검사를 붙였더니
**예전부터 있던 버그가 둘 걸렸다.** 둘 다 리팩터링이 만든 것이 아니라, 그동안 아무도 안 세던 것이다.

- **돌진전사** — 플레이어가 깊이 끝에 붙으면 벌린 줄이 벽으로 물려 두 줄이 같은 좌표로 접혔다.
  4-1(교차 돌진 3기)이 그 조합이다. 이제 벗어난 줄은 건너뛰고 다음 줄을 찾는다.
- **마법사** — 구석이 둘인데 셋을 세우면 0번과 2번이 같은 구석에 겹쳤고, 좌우 교대도 같은 주기라
  같은 점에 섰다. 4-2(마법사 3기 탄막)가 그 조합이다. 이제 셋째부터 안쪽으로 한 칸 물러난다.

둘 다 화면으로는 "적이 하나 덜 나온 것 같다" 정도로만 보인다. 적이 여섯이면 눈으로 못 센다.

## 4. 구현 순서

얇게 자른다. 5단계에 가서야 게임 동작이 처음 바뀐다.

1. ~~**순수 자료형.**~~ **완료.** `WaveSpawnEntry`와 enum 셋 (`WaveAuthoring.cs`).
2. ~~**자동 배치 순번 재정의.**~~ **완료.** `WaveLayout.AutoLaneIndices` · `Expand`,
   `WaveSpawnPlanner.PlanAuto` · `PlanAt`. 기존 아홉 웨이브를 두 경로로 돌려 좌표를 대조하는
   회귀 테스트가 붙어 있다(`WaveLayoutTests`).
3. ~~**씬 보드 컴포넌트와 지점 조회.**~~ **완료.** `StageWaveBoard`. 지금은 지점 표만 든다 —
   웨이브 목록 칸은 `WaveAsset`이 생기는 4단계에 붙인다.
   확정한 규칙: 같은 이름이 여럿이면 **먼저 붙은 것**을 쓰고, 자리가 안 꽂힌 줄은 건너뛴다.
   앞뒤 공백은 양쪽 다 무시한다. 실수 넷(빈 이름 · 중복 · 자리 없음 · 방 밖)은
   `Issues()`가 줄 번호까지 달아 목록으로 돌려주고, 로그는 그 위에 얹는다 — 로그는 검사할 수가 없다.
4. ~~**`WaveAsset`과 굽기 스크립트.**~~ **완료.** `WaveAsset`, `WaveAssetBuilder`.
   `Assets/Data/Waves/Wave_{스테이지}_{번호}.asset` 아홉 개를 구웠다.
   보드에 웨이브 목록 칸이 붙었고, 웨이브가 부르는 지점 이름을 표와 대조하는 검사도 여기서 들어갔다.
5. ~~**세 씬에 보드를 놓고 디렉터가 보드를 읽는다.**~~ **완료.** 여기서 게임이 바뀌었다.
   디렉터는 이제 `WaveAsset`만 안다. 되돌릴 스위치(`useLegacyTable`)를 켜면 옛 표를 애셋으로
   변환해 같은 경로로 흘린다 — 디렉터 안에 경로를 두 벌 두지 않기 위해서다. 8단계에서 없어진다.
   씬 배선은 `StageWaveWiringTests`가 지킨다.
6. ~~**땅속 돌출 모션.**~~ **완료.** `BurrowRules` · `SpawnBurrow` · `EntranceDirector.PlanBurrow`.
   `EntranceSpec`에 `startDepth` 한 칸을 더했다 — `height`는 양 끝점에 똑같이 걸리고
   `Physics.Teleport`는 음수 높이를 0으로 물려서, 기존 칸으로는 "아래에서 위로"를 표현할 수가 없다.
   소환 창구도 여기서 합쳤다(`EnemySpawnService.Spawn`이 모션으로 갈래를 고른다).
   **예고는 저작 항목이 아니라 디렉터가 항상 붙인다** — 켜고 끄게 두면 언젠가 꺼진 채로 나간다.
   예고를 낼 시간조차 없는 이른 등장은 `BoardProblem.BurrowTooEarly`가 잡는다.
7. ~~**`WaveAdvance` 배선.**~~ **완료.** `WaveClearRules` + `WaveCensus`.
   디렉터 안에 있던 종료 판정을 **순수 함수로 떼어냈다** — 아레나의 `RoundClearRules`와 같은 자리다.
   조건이 늘어날 자리가 거기 한 군데뿐이어야 테스트가 따라온다.
   미구현 조건은 런타임에서 전멸로 접고(안 접으면 스테이지가 영영 안 끝난다),
   저작 시점에는 `BoardProblem.UnsupportedAdvance`가 말해 준다.
8. ~~**하드코딩 표 제거.**~~ **완료.** `StageWaveCatalog.For`, `WaveDefinition`, `WaveSpawn`,
   디렉터의 되돌릴 스위치, 굽기 스크립트까지 지웠다. `StageWaveCatalog`에는 스테이지 지형
   (개수 · 아레나 번호 · 주제 · 토큰 상수)만 남았다 — 그쪽은 `GameManager`와 아레나가 함께 읽는다.
   **굽기 스크립트를 남기지 않은 이유**: 표가 없어지면 애셋이 원본이라, 굽기를 한 번 잘못 누르면
   손으로 저작한 웨이브를 통째로 잃는다. 자리 규칙만 `WaveAssetPaths`로 남겼다.
   기획서의 사본 노릇은 `WaveAssetContentTests`가 이어받았다 — 보는 대상만 표에서 애셋으로 바뀌었다.

아레나로 도는 2 · 5스테이지는 이 계획의 범위 밖이었다. 그쪽은 웨이브가 아니라 라운드로 돌았고
표가 따로 있었다. **그 흡수는 이후에 실제로 일어났다** —
[Stage_Encounter_Unification_Plan.md](Stage_Encounter_Unification_Plan.md)가 그 기록이다.
스폰 창구를 여기서 합쳐 둔 것이 그때 값을 했다.

## 5. 씬을 재생해서 눈으로 볼 것

테스트로 못 잡는 것들이다.

- ~~땅속 돌출 예고가 발밑에 보이는가.~~ **확인함.** 붉은 표식이 지점에 뜨고 몸보다 먼저 뜬다.
- **남은 문제: 반만 가려지지 않는다.** 이 프로젝트의 정렬은 순서값 하나라 스프라이트의
  아랫부분만 바닥으로 가리는 방법이 없다. 지금은 완전히 숨김에서 완전히 보임으로 한 번에 넘어간다
